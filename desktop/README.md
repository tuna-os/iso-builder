# TunaOS Media Writer

Native desktop apps for people whose browser cannot build an ISO on
[iso.tunaos.org](https://iso.tunaos.org): pick a desktop and a base, the app
builds the live ISO locally with the same tacklebox engine the website uses,
and writes it to a USB stick (or just saves the `.iso`). No terminal, no Go
toolchain, no `build-request.json` juggling.

| Directory | What | Owner |
|---|---|---|
| [`PROTOCOL.md`](PROTOCOL.md) | The JSON Lines contract between the GUIs and the helper | helper |
| [`helper/`](helper/) | `tunaos-media-helper` (Go) + the engine build tool | helper |
| [`macos/`](macos/) | SwiftUI app → `TunaOS-Media-Writer-macOS.dmg` | macOS |
| [`windows/`](windows/) | WinUI 3 app → `TunaOS-Media-Writer-Windows-x64.msi` | Windows |
| [`linux/`](linux/) | GTK4/libadwaita app + Flatpak → `TunaOS-Media-Writer-Linux-<arch>.flatpak` | Linux |

Per-platform build and test instructions live in each platform's README.

## The two binaries every app ships

Every app bundles **two** executables side by side:

- `tunaos-media-helper[.exe]` — the backend the GUI spawns (`version`,
  `catalog`, `build`, `drives`, `write`; see [`PROTOCOL.md`](PROTOCOL.md)).
- `tunaos-media-engine[.exe]` — tacklebox's own `cmd/purebuild`, built from
  the tacklebox version pinned in [`helper/go.mod`](helper/go.mod), which must
  equal `native/go.mod`'s pin (a test enforces it). The helper finds it next
  to its own executable (override: `TUNAOS_MEDIA_ENGINE`).

```bash
cd desktop/helper
# helper: plain cross-compile
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -trimpath -o DIR/tunaos-media-helper ./cmd/tunaos-media-helper
# engine: pass the target as flags, NOT as GOOS/GOARCH in the environment
go run ./cmd/build-engine -goos darwin -goarch arm64 -o DIR/tunaos-media-engine
```

Why a second binary: the engine's packages live under `tacklebox/internal/`,
which Go forbids importing from another module, so the helper drives the same
entry point the website's old fallback told users to `go run`. `build-engine`
builds it the way CI builds the website's `tbox.wasm` — inside tacklebox's own
module at the pinned version, so its dependencies are exactly tacklebox's
`go.sum` — from the hash-verified module cache copy. At the pinned version
`purebuild` declares `punchReader` only for Linux and does not compile for
macOS or Windows; `build-engine` adds
[`punch_other.go.txt`](helper/cmd/build-engine/punch_other.go.txt) (a plain
reader for `--rootfs-tar`, a flag the Media Writer never passes) to the copy.
No tacklebox file is modified. Upstreaming that file to tacklebox removes the
shim.

`media-writer-helper.yml` uploads both binaries for darwin/arm64,
darwin/amd64, windows/amd64, linux/amd64 and linux/arm64 as
`tunaos-media-helper-<os>-<arch>`.

## How the helper builds

- **Same request as the website.** For `--target ID` the helper constructs
  BuildRequest v1 byte-for-byte as `app/public/app.js` `buildRequestFromForm`
  does for that guided-picker selection: pinned `resolvedInputs`, the
  builder-config `default_flatpaks` of the target's desktop, `outputFilename`,
  label, `catalogVersion`, and `qualificationId` for browser-qualified
  targets. `helper/internal/buildreq/testdata/requests.json` is generated by
  running the real app.js functions in a Node VM
  (`gen-fixtures.cjs`) and the Go test compares bytes.
- **One intentional difference:** the browser fetches through its CORS relay
  (`https://relay.tunaos.org`, which fronts ghcr.io only). A native process
  needs no CORS, so the helper hands the engine `registry:
  https://ghcr.io` instead — for `--request` files too. Every digest pin is
  unchanged, so the engine verifies the same bytes, and native downloads do
  not spend the relay's bandwidth.
- **Catalog.** Fetched from `--base-url` (default `https://iso.tunaos.org`);
  if that fails, the copy embedded at build time is used and a `log` warn
  says so. Refresh the embedded copy and the parity fixtures with
  `go generate ./...` in `desktop/helper` (needs Node); CI warns when they
  lag `app/public`.
- **Free space.** Checked before anything is downloaded. Model (see
  `helper/internal/engine/space.go`): unpacked tree ≈ 3.0 × compressed size;
  scratch needs tree + compressed + 1 GiB, the ISO tree + compressed +
  256 MiB, both together when they share a volume. Calibrated on a real
  build of `flounder-sid:xfce` (compressed 1.16 GB → tree 2.94 GB, ISO
  4.43 GB); the model asked for 10.6 GB where the real peak was ≈8.9 GB
  (≈4.5 GB of scratch still present while the 4.43 GB ISO was written).
- **Scratch.** A fresh directory under the OS user cache dir (or under
  `--workdir`), always removed — on success, failure and cancel. The ISO is
  written as `<out>.partial` and renamed only after it is complete and
  hashed.

## How the helper writes

`write` re-enumerates right before writing and refuses with `device-changed`
unless the drive id's path, exact size and serial (when both sides report
one; the model on macOS, which has no serial in `diskutil`) still match. It
writes 4 MiB chunks at aligned offsets, zero-pads the final chunk to 4096
bytes (never past the device end), fsyncs, drops the read cache (Linux),
reads the image back and compares SHA-256, then ejects.

| | Unmount / lock | Device | Elevation | Eject |
|---|---|---|---|---|
| macOS | `diskutil unmountDisk` | `/dev/rdiskN` | GUI runs the helper with administrator privileges | `diskutil eject` |
| Windows | `FSCTL_LOCK_VOLUME` + `FSCTL_DISMOUNT_VOLUME` on every volume of the disk, held until done | `\\.\PhysicalDriveN` | GUI launches the helper with `runas` | `IOCTL_STORAGE_EJECT_MEDIA` |
| Linux | the GUI, through udisks2 | `--fd N` from udisks2 `Block.OpenDevice` (read-write: verify reads through the same fd) | polkit, via udisks2 | the GUI, through udisks2 |

The drive filters are `native/blockdev_*.go`'s, ported unchanged in their
decisions and unit-tested on every OS. On Linux the input now comes from
`/sys/block` and `/proc/self/mountinfo` instead of `lsblk`, which the
Flatpak sandbox does not have.

**Test devices.** Binaries built with `-tags testdevices` also list the
paths in `TUNAOS_MEDIA_HELPER_TEST_DEVICES` (comma-separated files or loop
devices) as drives. Release builds do not contain that code (a test asserts
it). Never ship a `testdevices` build.

## End-to-end proof (Linux host, 2026-11-10)

```
$ tunaos-media-helper build --target flounder-sid:xfce:linux/amd64 --out …/flounder-sid-xfce-linux-amd64.iso
{"event":"done","path":"…/flounder-sid-xfce-linux-amd64.iso","bytes":4427501568,"sha256":"dcc211d7516cbe4df769819adb4cbff38f7386f8453ba6f1ca2fa49c781a09f8"}
$ exec 7<>/dev/loop0   # 4496293888-byte loop device, as udisks2 would hand over
$ tunaos-media-helper write --iso …/flounder-sid-xfce-linux-amd64.iso --device '/dev/loop0|4496293888|test' --fd 7
{"event":"done","device":"/dev/loop0","bytes":4427501568,"verified":true}
$ head -c 4427501568 /dev/loop0 | sha256sum
dcc211d7516cbe4df769819adb4cbff38f7386f8453ba6f1ca2fa49c781a09f8  -
```

The host had 4.6 GB free on disk and a 12 GB tmpfs, so the proof used the
smallest catalog desktop that builds today. `flounder:xfce` (smaller still)
fails in the engine — and therefore on the website too — because the
published catalog snapshot pins a base the current live overlay was not built
against (`live overlay base digest mismatch`).

## Releasing

Push a tag `media-writer-vX.Y.Z`. `media-writer-release.yml` calls
`media-writer-{macos,windows,linux}.yml`, checks that exactly the asset names
above exist, writes `SHA256SUMS` and creates the release. Dispatch it with
`dry_run: true` (the default) to do everything but publish; the assets then
come back as one artifact. Signing and notarization run inside each platform
workflow only when its secrets are configured; their job summaries say
whether an artifact is signed.
